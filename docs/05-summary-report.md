### 分支策略

| 分支 | 用途 | 保护规则 |
|------|------|----------|
| main | 最终成果，只接受来自dev的合并 | 不允许直接push |
| dev | 集成分支，各feature合并至此 | 合并前需解决冲突 |
| feature/* | 各成员独立开发分支 | 完成后合并至dev |

### 提交与合并规则

- 提交信息格式：`类型: 简要描述`（feat / docs / fix / merge / resolve）
- 提交人名称统一使用本人姓名拼音全称
- feature 分支完成后由负责人合并至 dev，合并前须在本地解决所有冲突
- dev 稳定后由项目经理（yangyuxuan）合并至 main
- 所有合并保留完整提交记录，不使用 `--squash`

### 分支使用过程

1. 在main基础上创建dev集成分支
2. 各成员从dev创建feature分支独立工作：
   - `feature/wbs`：liming负责WBS与进度计划
   - `feature/config`：chenwei负责配置管理方案
   - `feature/summary`：yangyuxuan负责总结报告
3. 各feature分支完成后合并至dev，解决冲突后再合并至main

## 五、冲突解决过程

> **说明：本小组为单人成组，采用"同一仓库中创建两个分支，在不同时间分别修改同一文件同一位置"的方式模拟多人冲突场景。**

### 冲突产生原因

本人分别在`feature/wbs`分支（以liming身份）和`feature/config`分支（以chenwei身份）修改了`docs/conflict.md`文件中"协作规范"部分的同一行内容，两次修改在不同时间完成，合并至dev时产生冲突。

### 处理方式

1. 执行`git merge feature/config`时，Git提示`docs/conflict.md`存在冲突
2. 打开冲突文件，查看`<<<<<<<`、`=======`、`>>>>>>>`标记
3. 手工编辑，保留双方内容并整合为最终版本
4. 执行`git add docs/conflict.md`标记冲突已解决
5. 执行`git commit`完成合并提交

### 最终结果

冲突成功解决，合并提交记录完整保留在dev分支，后续合并至main时无新冲突。
