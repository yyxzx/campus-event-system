## 二、WBS分解思路

WBS采用交付物导向原则，以最终成果为分解主线，共分为四个一级条目：

1. **项目管理文档**：涵盖项目概况、WBS、进度计划、配置管理四类文档
2. **版本仓库与目录结构**：包括仓库初始化和分支结构建立
3. **协作过程成果**：包括冲突制造与解决、分支合并记录
4. **总结报告**：全体成员共同完成并提交至main分支

每个一级条目均分解至L3级，确保每个最小成果单元可管理、可验证。分解过程中严格避免以"开会""讨论"等纯动作作为分解主线。

---

## 三、进度安排依据

进度计划从WBS中提取9项关键活动，按前置关系排列：

- 仓库初始化（A1）为所有工作的起点
- WBS完成（A3）是进度计划（A4）和配置管理（A5）的前置条件
- 冲突解决（A7）必须在分支建立和配置方案完成后进行
- 总结报告（A8）在冲突解决后由全体成员共同完成

整体计划跨度4天（2026-05-12至2026-05-15），设置4个里程碑节点。

## 四、配置管理过程

### 配置项识别

共识别7项主要配置项，涵盖README、四类文档、总结报告和冲突练习文件。

### 分支使用过程

1. 在main基础上创建dev集成分支
2. 各成员从dev创建feature分支独立工作：
   - `feature/wbs`：liming负责WBS与进度计划
   - `feature/config`：chenwei负责配置管理方案
   - `feature/summary`：yangyuxuan负责总结报告
3. 各feature分支完成后合并至dev，解决冲突后再合并至main

## 五、冲突解决过程

### 冲突产生原因

liming在`feature/wbs`分支和chenwei在`feature/config`分支分别修改了`docs/conflict.md`文件中"协作规范"部分的同一行内容，导致合并至dev时产生冲突。

### 处理方式

1. 执行`git merge feature/config`时，Git提示`docs/conflict.md`存在冲突
2. 打开冲突文件，查看`<<<<<<<`、`=======`、`>>>>>>>`标记
3. 手工编辑，保留双方内容并整合为最终版本
4. 执行`git add docs/conflict.md`标记冲突已解决
5. 执行`git commit`完成合并提交

### 最终结果

冲突成功解决，合并提交记录完整保留在dev分支，后续合并至main时无新冲突。
